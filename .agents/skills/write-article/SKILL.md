# Write an article

Turn the user's approved outline or source material into article prose.
Preserve the author's point of view and any passages the user asked to keep.
Do not expand the scope beyond the requested article.

## Shape the story

Use first-person narration for the author's experience.
Explain the situation, the friction it caused, the decision the author made, and what changed afterward.
Write concrete, elaborative paragraphs that let the reader follow how the problem appeared during work.
Avoid compressed summaries that name a problem without showing how it affected a task.
Use generic examples across different tasks when requested, rather than claiming a single specific codebase or task represents the whole experience.

For an article about a workflow that evolved over time, show capabilities accumulating in increments.
Use `Phase N` prefixes for phase headings and split long phases into meaningful subsections.
Make each phase's problem lead naturally to the change introduced in that phase.
Keep examples and claims within the author's supplied experience.
Do not invent dates, metrics, quotations, or personal events.

Use the user's requested terminology consistently.
Keep workflow diagrams or orchestration notation out of the prose when the user has reserved them for visuals.
Keep the conclusion simple when the user asks for a simple conclusion.

## Markdown source

Put each full sentence on its own source line in long Markdown articles.
Preserve blank lines between paragraphs and normal Markdown heading structure.
